# SDAI Digitalization

A benchmarking and extraction pipeline for government administrative documents in low-resource settings. The project evaluates multiple OCR engines and vision-language models (VLMs) on scanned documents written in French and Arabic, and exposes the results through a structured API and an interactive dashboard.

## Context

Digitalization programs in sub-Saharan Africa often face documents that are:

- Multilingual (French administrative language alongside Arabic)
- Physically degraded (faded ink, flag watermark interference, handwritten annotations)
- Produced on typewriters or older printing equipment
- Lacking digital originals or metadata

This project provides a repeatable pipeline to measure which combination of preprocessing + extraction model performs best on such material, and to build a review interface where human operators can validate extracted fields at scale.

## What it does

### 1 — OCR benchmarking (`ocr_test.py`)

Runs three engines on every document image, both raw and after preprocessing (grayscale → denoise → Otsu binarisation):

| Engine | Notes |
|--------|-------|
| **Tesseract** | Fast, CPU-only, `fra+ara` language pack |
| **EasyOCR** | Separate Latin and Arabic readers, GPU-optional |
| **Surya** | Layout-aware, highest accuracy on complex layouts |

Outputs per-document JSON with extracted text, confidence score, and processing time for each engine × variant combination.

### 2 — VLM structured extraction

Two scripts drive field extraction using vision-language models:

| Script | Model | Runtime |
|--------|-------|---------|
| `vlm_local_test.py` | `Qwen/Qwen2-VL-2B-Instruct` (HuggingFace, ~15 GB first run) | CPU / MPS — 8 GB RAM minimum |
| `vlm_ollama_test.py` | `qwen2.5vl:7b` (Ollama) | GPU recommended |

Both models are prompted to return a structured JSON object with:

```
document_type · reference_number · date · person_names · functions
destination_or_subject · organisation · signatory · budget_line
language · bilingual_layout · quality_issues · extraction_confidence
```

`extraction_confidence` (`high / medium / low`) drives a **discriminated union** in the TypeScript types so the dashboard can render each tier differently with full type safety.

### 3 — Anonymization tool (`preprocessing/anonymize.py`)

Interactive OpenCV tool for redacting sensitive regions (names, IDs) before storing documents. Draws black rectangles over selected areas and saves the anonymized version.

### 4 — Dashboard + API

A review interface served from Docker:

- **FastAPI** serves pre-computed JSON results and document images.
- **React dashboard** shows the VLM extraction fields and the full OCR engine comparison side by side with the document image.
- Switching tabs between *VLM Extraction* and *OCR Comparison* fetches only the relevant data. A green dot in the sidebar marks documents that have been processed.

## Running with Docker (recommended)

Docker is the fastest way to get the dashboard and API running without installing Python or Node dependencies.

```bash
docker compose up --build
```

The dashboard is available at **http://localhost**.

> The `documents/` folder is mounted read-only into the API container at runtime. The images and JSON result files must exist there before starting — they are generated by the Python scripts (see below).

To expose the API directly (useful for debugging):

```bash
# Uncomment the ports section in docker-compose.yml, then:
docker compose up --build
# API available at http://localhost:8000
```

## Running locally (development)

### Prerequisites

| Tool | Version |
|------|---------|
| Python | 3.11 |
| Node.js | ≥ 18 |
| pnpm | ≥ 9 (`npm install -g pnpm`) |
| Tesseract | system package (`brew install tesseract tesseract-lang` on macOS) |
| Ollama | for `vlm_ollama_test.py` (`brew install ollama`) |

### Python environment

```bash
python3.11 -m venv venv311
source venv311/bin/activate
pip install pytesseract easyocr surya-ocr opencv-python pillow
pip install fastapi "uvicorn[standard]"

# For the local VLM script only:
pip install transformers torch qwen-vl-utils
```

### OCR benchmarking

```bash
source venv311/bin/activate

# Place document images in documents/anonymized_docs/
python ocr_test.py
# Results written to documents/ocr_results/json/
```

### VLM extraction

```bash
# Option A — Ollama (recommended, faster)
ollama pull qwen2.5vl:7b
python vlm_ollama_test.py
# Results written to documents/ocr_results/json/vlm_qwen25_results.json

# Option B — Local HuggingFace model (~15 GB download on first run)
python vlm_local_test.py
# Results written to documents/ocr_results/json/vlm_local_results.json
```

### API server

```bash
source venv311/bin/activate
CORS_ORIGINS=http://localhost:5173 uvicorn api_server:app --reload --port 8000
```

### Frontend

```bash
pnpm install
pnpm dev
# Dashboard at http://localhost:5173
```

## Testing

The project has two independent test suites: Python (pytest) for the API server, and TypeScript (vitest) for the Zod schemas.

### Python — API server tests

Tests cover all auth flows, OCR and VLM endpoint behaviour, image serving, and auth-guard enforcement. The filesystem is fully mocked with temporary directories — no real documents or result files are required.

```bash
# Install test dependencies (once)
pip install -r requirements.test.txt

# Run all API tests
pytest tests/ -v

# Run a specific file
pytest tests/test_auth.py -v

# Run with coverage (needs pytest-cov)
pip install pytest-cov
pytest tests/ --cov=api_server --cov-report=term-missing
```

Or via the root package.json shortcut:

```bash
pnpm test:api
```

### TypeScript — Zod schema tests

Tests cover `parseVlmResult` (all confidence tiers, error cases, field fallbacks) and all Zod schemas in `@sdai/types`.

```bash
# Install workspace deps (once)
pnpm install

# Run TypeScript tests
pnpm --filter @sdai/types test

# Or run all package tests from the root
pnpm test
```

### Running both at once

```bash
pnpm test && pnpm test:api
```

## API reference

All routes are read-only (`GET`).

### OCR

| Route | Description |
|-------|-------------|
| `GET /api/documents` | List of all documents with OCR availability flag |
| `GET /api/documents/{filename}` | Full OCR result for one document (raw + preprocessed, all 3 engines) |
| `GET /api/results` | Combined result file for all documents |

### VLM

| Route | Description |
|-------|-------------|
| `GET /api/vlm/documents` | List of documents with VLM availability flag |
| `GET /api/vlm/documents/{filename}` | VLM extraction result for one document |
| `GET /api/vlm/results` | All VLM results |

### Images

| Route | Description |
|-------|-------------|
| `GET /images/raw/{filename}` | Original document image |
| `GET /images/preprocessed/{filename}` | Binarised image used for OCR |

## TypeScript package architecture

The frontend is a pnpm monorepo. Shared code lives in packages consumed by the dashboard:

**`@sdai/types`** — Zod schemas parsed at the API boundary. The core type is a discriminated union on the VLM confidence tier:

```typescript
type ExtractionResult =
  | { tier: "high";   filename: string; fields: { document_type: string; quality_issues: string[]; … } }
  | { tier: "medium"; filename: string; fields: DocumentFields }
  | { tier: "low";    filename: string; fields: DocumentFields }
  | { tier: "failed"; filename: string; error?: string; is_parse_error: boolean }
```

**`@sdai/api-client`** — typed `fetch` wrappers for every API route. Responses are validated with the Zod schemas before being returned to the calling hook.
